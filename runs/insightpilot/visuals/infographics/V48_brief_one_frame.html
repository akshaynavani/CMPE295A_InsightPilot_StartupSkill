InsightPilot · Founder brief

One brief, so the PRD, the market sizing and the whitepaper describe one company

Conversational business intelligence for enterprise data analysts that turns a business question into a planned, executed and fully traceable analytical workflow, through a multi-agent orchestration layer.
One adaptive system, three edges
Low edge
Business manager, the requesterNeeds a plain-language answer, cannot judge correctness, never writes a queryJustifies the conversational interface. Without this edge, natural language is decorative for a beachhead fluent in SQL
Beachhead
Enterprise data analystCompress the per-question overhead while keeping control and verifiabilityThe user the entire pack is written for
High edge
Staff data scientistAudit lineage, override the model's target and algorithm, extend the pipelineMakes traceability and override load-bearing rather than cosmetic
The user is not the payer. The analyst is the user and the champion. The economic buyer owns the analytics function's budget, and monetisation is modelled hypothetically only.

The problem, and what it is not
Each ad-hoc question costs the same manual sequence: locate the source, inspect the schema, write and debug the query, clean and join, choose a chart, interpret, and build a model when the question is predictive. The requester waits and the analyst context-switches away from planned work. The pain is latency and analyst attention, not an absence of tooling. This beachhead already owns a BI stack and can write SQL. What they cannot compress is the fixed per-question overhead, and what they cannot easily do at all is the modelling step.
The mechanism
question→ plan→ execute→ answer plus lineage→ follow-up
Data fetch and integrationPostgres, CSV and Excel, REST JSON
Analyticsprofiling, reconciliation, statistics
Visualizationchart chosen from the data shape
MLtime-boxed, with an explicit not-attempted list
Replanning fires when an agent's result invalidates the plan, rather than the run continuing into nonsense. The connector layer sits behind interfaces so another source plugs in later if time permits.
Two sections left deliberately empty
✕
No single ten-times claim. All four agents are built together. A decision, not an oversight: the pack gains technical breadth appropriate to a two-semester capstone and forgoes a sharp differentiator. Downstream artifacts must not manufacture one to fill the gap.
✕
No moat declared. With an open-source core the code is not the asset. The strongest candidate is a learned semantic layer, where copyable code sits on non-copyable semantics. Confirming evidence would be acceptance rate rising over time with no model change, and until then the section stays empty.
Why now, and it is asserted not sourced
1
Tool-use and replanning reliability crossed a usable threshold. The architecture was expressible before and was not dependable. Multi-step loops compounded error past the point where a chained workflow could be trusted without a human at each hop.
2
Tool access standardised. Connector integration became a configuration problem rather than bespoke engineering per source, which is what makes a pluggable layer tractable for a small team.
Both are founder-asserted, and the research phase has to date and source them rather than inherit the claim.

No domain experience inside an enterprise analytics function, so the problem statement is researched rather than lived and the research phase has to source it.
The riskiest assumption

Multi-agent planning is reliable enough end to end that error compounding across fetch, analyse, model and visualise does not make the output untrustworthy.

If it is false, nothing above matters: an analyst who must re-verify every answer has been given work rather than leverage. It is well matched to the first-semester spike, which tests it directly on one narrow path instead of deferring it.
